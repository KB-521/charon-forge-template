# 前端代码评审

系统性评审当前仓库前端代码的功能正确性、类型安全、交互完整性与可维护性。

## 调用方式

- `web/code-review` 默认不在前端实现完成后自动执行。
- 仅在用户明确要求 code review、提交前 review、PR review 或问题排查时调用。

## 评审优先级（必须按顺序）

| 优先级 | 检查项 |
| --- | --- |
| 🔴 P0 | 功能正确性（需求偏差、边界行为、表单/流程错误） |
| 🔴 P0 | 数据一致性（API 类型、mock、页面状态不一致） |
| 🟡 P1 | SSR/CSR 边界与 Hook 使用错误 |
| 🟡 P1 | 加载态/空态/错误态缺失 |
| 🟢 P2 | 可维护性（命名、重复逻辑、组件职责） |

## 关键检查清单

### 1) 正确性

- 交互流程是否与需求一致。
- 成功、失败、空数据、边界值是否覆盖。
- 表单默认值、禁用态、回退逻辑是否正确。

### 2) 数据与类型一致性

- `src/api` 类型定义是否与页面使用一致。
- mock 返回结构是否与接口类型一致。
- 页面是否绕过接口层直接拼装数据。

### 3) SSR/CSR 与 Hook

- 是否在服务端渲染路径错误使用客户端状态订阅。
- `useSyncExternalStore` 是否提供 `getServerSnapshot`。
- Effect 订阅、事件绑定、定时器是否正确清理。

### 4) 交互完整性

- 是否具备 loading、empty、error 三态。
- 异步请求是否避免重复提交、竞态覆盖。
- 是否存在明显闪烁、状态回跳、hydration 风险。

### 5) 可维护性

- 页面、组件、hook、store 职责是否清晰。
- 是否存在重复请求、重复转换、硬编码常量。
- 命名与目录落点是否符合项目约定。

## 评审流程

1. 明确上下文：需求、设计、影响范围。
2. 先看高层数据流：页面 → 组件/hook/store → API/mock。
3. 再看细节：状态流转、副作用、边界行为、交互完整性。
4. 核对类型与 mock：接口定义、mock 返回、页面消费是否一致。
5. 最后核对校验：lint、类型检查、手动回归是否覆盖核心风险点。
6. 输出结论：按严重级别列出问题与修复建议。

## 输出格式（必须）

```markdown
## 代码评审：<模块/页面/PR 名称>

### 结论
[通过 / 需要修改 / 阻塞]

### 发现的问题（按严重级别）
- 🔴 [绝对路径:行号] 问题描述
  - 风险：...
  - 建议：...
- 🟡 [绝对路径:行号] 问题描述
  - 风险：...
  - 建议：...

### 待确认项
- ...

### 正向反馈
- ...
```

## 评审纪律

- 只评论可验证事实，避免主观风格争论。
- 每条问题必须说明“风险 + 建议”。
- 优先给最小修复路径，避免一次性大改。
- 未确认信息明确标注“待确认”，不做武断结论。
