# 前端技术方案设计

将需求转成可执行的前端实现方案，重点解决“页面怎么拆、页面对应的业务逻辑，以及页面所包含的后端接口”。

## 何时使用
- 需求已明确，需要输出前端可实施方案。
- 页面多角色、多状态、多流程，直接开工风险高。
- 需要在开发前冻结路由、组件边界、状态模型与前端权限口径。

## 工作流

1. **分析输入**
- 输入：PRD、原型/Figma、审查结论、现有前端实现约束。
- 提取：页面清单、用户流程、角色差异、关键状态、数据依赖。
- 输出待确认项（问题、选项、影响、推荐）并先确认核心口径。

2. **调研现有实现**
- 检查 `src/app`、`src/components`、`src/stores`、`src/hooks`、`src/api` 现有模式。
- 记录“可复用模式 / 不适用原因 / 本次影响”，避免重复造轮子。

3. **方案设计**
- 信息架构：页面/路由/导航层级与入口关系。
- 页面拆分：按页面维度输出独立设计单元，至少明确“页面目标、业务逻辑、关键交互、状态边界”。
- 数据契约：前端 ViewModel 与 API 字段映射、容错与降级策略。
- 页面接口映射：每个页面必须给出接口清单（接口路径、方法、用途、触发时机、错误兜底）。
- 权限与可见性：页面级、组件级、动作级权限与兜底策略。

4. **文档产出**
- 按 `references/template.md` 产出方案文档。
- 明确记录“待确认 + owner + 截止时间”。
- 关键结论必须可追溯到 PRD、原型或既有实现。
- 若当前变更包包含多个设计包，方案文档落到 `design/<design-package>/`，并同步维护根 `design/INDEX.md` 与子目录 `INDEX.md`。

5. **评审与门禁**
- 无未处理 BLOCKER 才可进入开发。

## 输出

- 主文档：`ai-workflow/sdd/changes/<change-id>/design/<design-package>/<project>-frontend-solution.md`，单一小变更可落在 `design/<project>-frontend-solution.md`。
- 同一设计包内的前端方案默认集中在上述单一文档中；跨功能域或跨设计包时，用 `design/<design-package>/INDEX.md` 分包承接，不把多个功能域硬塞进一份文档。

模板见 `references/template.md`。

## 规则
- 优先复用项目既有前端模式，不引入无必要新范式。
- 方案必须按页面维度拆分，禁止仅按模块泛化描述。
- 每个页面必须同时给出业务逻辑和接口调用信息，缺一视为不完整。
- 每个页面必须定义 `loading / empty / error / no-permission` 四类状态策略。
- 图片与原型链接必须绑定到对应功能点，禁止脱钩引用。
- 对未定义项标注“待确认”，不主观补规则。
- 发现关键不确定项时先确认，再继续推进方案定稿。
