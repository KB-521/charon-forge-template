# 前端任务实现 Skill

## 目标
统一前端任务实现流程，确保先打通数据层，再落页面，避免“页面先写、接口回填”导致反复改动。

## 强制执行顺序（必须按顺序）

```
需求输入
  -> Step 0. 业务逻辑与规则对照
  -> Step 1. 实现接口
  -> Step 2. 实现接口 Mock
  -> Step 3. 实现页面
  -> Step 4. 自检
  -> Step 5. 交付
```

### Step 0. 业务逻辑与规则对照（先做）
1. 从 PRD、PRD review、需求卡、设计/API 契约抽取“动作级业务逻辑 + 字段级规则”。
2. 动作级业务逻辑必须覆盖：触发动作、成功路径、失败路径、回退策略。
3. 字段级规则必须覆盖：必填、长度、匹配方式（精确/模糊）、默认值、边界行为。
4. 如口径冲突，先修正文档口径再进入 Step 1。
5. 产出要求：
   - 业务逻辑对照表（来源一致性）；
   - 字段规则对照表（来源一致性）；
   - 规则实现落点（接口参数、mock 行为、页面输入约束）。

### Step 1. 实现接口（先做）
1. 使用 `api-impl` skill 实现接口。

### Step 2. 实现接口 Mock（第二步）
1. 使用 `api-mock skill` 为 Step 1 的接口逐个补齐 mock。
2. mock 返回结构必须与接口类型一致，不允许页面层自行拼装假数据。
3. 产出要求：
   - 关键页面路径涉及接口全部可命中 mock；
   - 异常场景至少包含：空数据、失败响应。

### Step 3. 实现页面（最后做）
1. 页面只能调用 Step 1 的接口封装，不允许直接写请求或写死数据。
2. 页面中的样式实现统一使用 Tailwind CSS。
3. 产出要求：
   - 页面交互与需求一致；
   - 成功/失败/边界行为可复现。

### Step 4. 自检
1. 不自动执行 `web/code-review`。
2. 完成最小自检，至少覆盖：
   - API 类型、mock 与页面调用是否一致；
   - loading、empty、error、no-permission 是否按任务要求落地；
   - 关键交互路径是否可复现；
   - lint/类型检查是否按任务风险执行。
3. 若用户明确要求 code review，应作为独立任务调用 `web/code-review`，不作为本次实现后的自动动作。

### Step 5. 交付
1. 检查顺序是否被遵守：业务逻辑与规则对照 -> 接口文件 -> mock 文件 -> 页面文件 -> 自检。
2. 运行最小校验（至少变更文件 lint 通过）。
3. 输出时必须给出：
   - 业务逻辑对照与实现落点；
   - 字段规则对照与实现落点；
   - 接口变更文件列表；
   - mock 变更文件列表；
   - 页面变更文件列表；
   - 自检结果；
   - 剩余风险；
   - 校验结果。

## 门禁（Gate）
- Gate 0：未完成 Step 0，禁止开始 Step 1。
- Gate 1：未完成 Step 1，禁止开始 Step 2/3。
- Gate 2：未完成 Step 2，禁止开始 Step 3。
- Gate 3：未完成 Step 4 自检，禁止交付。
- Gate 4：最终输出必须体现五类产物（业务逻辑对照/字段规则对照/接口/mock/页面）和自检结论。
- Gate 5：执行后禁止自动调用 `web/code-review`，除非用户明确把 code review 作为独立任务。
