# 统一交互发布入口

方案索引ID：DES-BE-20261020-001

状态：用户已确认方案及增量模板选择要求；实现和本地验证已完成，真实外发待首次账号配置。

## 目标与使用方式

维护者提交并推送修改后，在终端运行 `pnpm release`。交互选择“模板 / CLI / 全部”，展示目标提交、版本与外发内容，确认后触发统一 GitHub Actions，并显示运行链接与最终结果。消费者继续使用 `npm create charon-forge@latest`。

## 方案比较

- 推荐：本地交互入口触发 GitHub Actions。统一执行环境与发布凭据，不要求维护者手动传批次、URL、首次发行标记或下载历史。
- 备选：仅在 Actions 页面点击发布。实现更少，但需要离开终端。
- 备选：全部本地执行。依赖本机环境、权限和网络状态，维护成本较高。

## 执行流程

1. 本地检查 GitHub CLI 登录状态、目标分支及远端提交，拒绝发布未提交或未推送的修改。
2. Actions 根据仓库推导固定下载地址，自动分配批次，读取全部正式历史并判断首次发布。
3. 对所有模板计算版本归一化的发布摘要，默认勾选新增和变化项，允许取消并选择 patch/minor/major/指定版本。只对选中模板执行隔离原生验证和生成正式附件；未选模板保留历史 URL。版本仅覆盖归档元数据，不回写源码；完整 catalog 保留全部历史。沿用现有协议与摘要校验，不覆盖已发布版本。
4. 串行发布模板 Release，下载核验后更新 Pages 的 stable 指针。CLI 按选择发布，已发布且内容相同的版本跳过，内容冲突报错。
5. 展示完成状态、版本与安装命令。失败保留日志；重试核对已有产物，不覆盖历史包，不因后一步失败回滚已经公开的包。

## 一次性配置

首次需要启用 GitHub Pages、确定 npm 包名与许可、建立 npm 发布身份及所需仓库权限，并写入固定分发源配置。认证细节在实施时按官方文档核对，不要求将密钥写入仓库。模板发布与 CLI 发布可分别使用；仅模板更新时无需重新发布 CLI。

## 实施与验证边界

实现交互命令、统一 workflow、可重试发布编排和精简发布说明。保留原底层准备脚本供自动化复用。验证首次/后续批次、只发模板、只发 CLI、重复版本、失败重试及远程生成链路；本地测试模拟外部 API，不真实发布。外发需另有明确授权。
