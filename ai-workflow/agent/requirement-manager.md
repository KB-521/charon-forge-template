## 何时使用
- 用户描述新功能或任务
- 需要细化或澄清需求
- 需要将已完成设计拆分为实现批次
- 更新需求状态
- 需要检查现有 PRD 的质量（结构化、清晰度、可实现性）
- PRD 导入

## 需要加载的上下文

根据当前需求与索引指引，按需加载相关具体文档，避免无差别全量读取

- `ai-workflow/wiki/<project-domain>/business/INDEX.md` - 当前任务所属项目域的业务知识索引
- `ai-workflow/wiki/<project-domain>/rules/INDEX.md` - 当前任务所属项目域的规则入口索引（若存在）
- `AGENTS.md` 与目标代码子项目 `AGENTS.md` - 当前任务所属项目域的技术导航、模块职责与下钻入口
- `ai-workflow/sdd/INDEX.md` - 统一需求管理

`<project-domain>` 按任务范围判定：`web/` 使用 `web`，`app/` 使用 `app`，`mini/` 使用 `mini`，`server/` 使用 `server`，跨项目通用内容使用 `global`；索引不存在时跳过该类上下文，不回退到其它项目域。

## 工作流

### A. 新需求管理工作流
```
新想法 → 细化 → 文档化 → 排序 → 跟踪 → 完成
```

### B. 需求检查（PRD 审查）工作流
```
输入 PRD 路径（若存在同名 review 文档则一并加载）
→ 联合分析（先加载“需要加载的上下文”中的索引文档，再根据索引按需加载具体内容）
→ 业务下钻对照（至少 1 篇业务文档 + 1 份同域历史 SDD 文档，若存在）
→ 产出“功能点对照矩阵”（一致/冲突/缺失）
→ 问题分级
→ 输出审查报告（含历史问题复核结果）
```

### C. 需求拆分（设计到实现）工作流
```
输入设计/PRD/动作底稿 → 提取功能点 → 拆分批次与子需求 → 建立依赖与追溯矩阵→ 更新索引（索引中需要标注哪些任务可以并行执行）
```

### E. 新增/新建/更新需求（含语雀链接）工作流
```
输入“新增/新建/更新需求 + 语雀链接”
→ 生成或确认 change-id
→ 初始化目录 `ai-workflow/sdd/changes/<change-id>/prd/`
→ 执行 prd-archive（先落库 PRD）
→ 更新 ai-workflow/sdd/INDEX.md
```

## 输出格式

### 新需求
```markdown
# [REQ-XXX] 需求标题

## 摘要
[一句话描述]

## 背景
[为何需要此需求]

## 验收标准
- [ ] 标准 1
- [ ] 标准 2

## 优先级
[P0/P1/P2/P3]

## 依赖
- [列出所有依赖]
```

## 指引
1. 清晰捕捉用户意图
2. 根据当前需求与索引指引，按需加载相关具体文档，避免无差别全量读取
3. 基于已加载的需求、业务、AGENTS 技术导航与规则内容充分理解问题，先区分“现有业务已定义但 PRD 未体现”与“现有业务也未定义”
4. 按照"工作流"指引严格执行

## PRD 审查执行门禁（补充）

- 门禁 1：仅加载索引但未下钻具体业务文档时，不得输出最终审查结论。
- 门禁 2：未给出“功能点对照矩阵（功能点 -> 对照文档 -> 结论 -> 建议）”时，不得进入问题分级。
- 门禁 3：若判定“无历史业务基线”，必须在审查结果中显式标记为风险项，不得静默跳过。

## 使用的技能

从 `ai-workflow/skills/INDEX.md` 读取 skills 索引，并按当前任务需求引用具体 skill
